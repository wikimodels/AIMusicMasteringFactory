# ТЗ: BPM Retimer — пакетный инструмент подгонки темпа

## 1. Назначение
Инструмент с дашбордом, который берёт папку с исходными аудиофайлами разных
форматов, определяет BPM каждого трека и растягивает/сжимает его по времени
(без изменения высоты тона) до целевого BPM — с опциональным случайным
разбросом вокруг цели, — сохраняя результат в указанном формате в отдельную
папку.

## 2. Входные данные
- **Папка с исходниками**, путь задаётся в дашборде.
  - Дефолт: `D:\GitHub\AIMusicMasteringFactory\bmp-retimer\input`
- **Поддерживаемые входные форматы:** WAV, MP3, M4A (минимум); желательно
  через FFmpeg — тогда почти любой контейнер зайдёт бесплатно (FLAC, OGG и т.д.)
- Рекурсивный обход подпапок — **уточнить**: нужен ли обход вложенных папок,
  или только файлы в корне указанной директории?

## 3. Выходные данные
- **Папка для готовых треков**, путь задаётся в дашборде.
  - Дефолт: `D:\GitHub\AIMusicMasteringFactory\bmp-retimer\output`
- **Формат вывода — выбирается в дашборде**, один или несколько одновременно:
  - WAV
  - MP3
  - M4A (AAC)
  - OGG (Vorbis/Opus) — **подтверждено**, заменяет исходно указанный
    WebP (WebP — формат изображений, для аудио не применяется)
- Имя выходного файла: `<исходное_имя>_<итоговый_bpm>bpm.<ext>`
  (например: `dark_jazz_intro_40bpm.wav`)

## 4. Параметры дашборда

| Параметр | Тип | Описание |
|---|---|---|
| Путь к папке input | текстовое поле / выбор папки | см. п.2 |
| Путь к папке output | текстовое поле / выбор папки | см. п.3 |
| Целевой BPM | число | целевой темп, к которому приводятся все треки |
| Разброс N (%) | число, ≥ 0 | см. логику ниже |
| Формат(ы) вывода | чекбоксы | WAV / MP3 / M4A / OGG (см. уточнение) |
| Кнопка "Старт" | кнопка | запуск обработки очереди |
| Список треков + прогресс-бар | таблица/список | см. п.6 |

## 5. Логика разброса BPM (ключевая механика)

Для **каждого трека отдельно**, независимо, вычисляется свой итоговый
целевой BPM по формуле:

```
итоговый_bpm(трек) = целевой_bpm * (1 + случайный_коэффициент)

где случайный_коэффициент — случайное число в диапазоне [-N/100, +N/100],
выбираемое заново для каждого трека (равномерное распределение).
```

**Пример:** целевой BPM = 40, N = 2 →
для каждого трека независимо выбирается случайное отклонение в пределах
±2% от 40, то есть итоговый BPM трека будет случайным числом в диапазоне
**39.2 – 40.8 BPM**, разным для каждого файла в очереди.

**Частный случай:** если N = 0 → разброса нет, все треки приводятся ровно
к целевому BPM без исключений.

**Формула подтверждена заказчиком — реализовывать строго по Варианту А**
(диапазон разброса ±N% от целевого BPM, случайный коэффициент равномерно
распределён внутри всего диапазона, выбирается заново для каждого трека).

## 6. Обработка очереди файлов
- Все файлы из папки input добавляются в список задач.
- Для каждого файла отображается:
  - Имя файла
  - Статус (в очереди / определение BPM / растяжение / сохранение / готово / ошибка)
  - Прогресс-бар (общий по всей очереди **и** индивидуальный по текущему файлу — уточнить, нужен ли индивидуальный, или достаточно общего)
  - Исходный BPM (определённый автоматически)
  - Итоговый BPM (с учётом разброса)
- Обработка может быть последовательной или параллельной (уточнить,
  критична ли скорость — параллельная обработка нескольких файлов
  одновременно ускорит процесс на многоядерных системах).

## 7. Определение BPM (технически)
- Автоматическое определение темпа исходного трека (beat tracking).
- **Важно:** автодетект BPM может ошибаться (например, определить
  удвоенный/половинный темп на медленных или "рубатных" треках без чёткой
  ритм-секции). Предусмотреть:
  - Возможность ручной корректировки определённого BPM перед стартом
    обработки (опционально, но полезно для контроля качества)
  - Логирование определённого BPM для каждого файла — чтобы можно было
    проверить постфактум, не съехало ли определение в 2 раза

## 8. Тайм-стретч (сам механизм растяжения)
- Изменение длительности трека без изменения высоты тона (питча).
- Предпочтительный движок: **Rubberband** (высокое качество, минимальные
  артефакты даже на сильном растяжении/сжатии).
- Фолбэк-движок (если Rubberband не установлен в системе): библиотека
  для тайм-стретча на основе phase vocoder (например, librosa) —
  ниже качеством на больших коэффициентах растяжения, но работает без
  внешних зависимостей.

## 9. Обработка ошибок
- Файл повреждён / не распознан формат → статус "ошибка" в списке,
  обработка остальных файлов очереди продолжается.
- Не удалось определить BPM → тот же принцип: ошибка по конкретному
  файлу, не блокирует остальные.
- Лог ошибок должен быть доступен для просмотра (файл лога или
  отдельная панель в дашборде).

## 10. Окружение проекта и управление зависимостями

- **Корень проекта:** `D:\GitHub\AIMusicMasteringFactory`
- Перед началом работы бот/разработчик должен зайти в корень проекта и
  ознакомиться с уже существующими конфигурационными файлами
  (например: `pyproject.toml`, `.env`, файлы настроек путей/параметров,
  если такие уже заведены) — новые настройки не должны дублировать или
  конфликтовать с уже существующей структурой проекта.
- **Управление Python-зависимостями — через Poetry.**
  - Новые пакеты (librosa, soundfile, и т.д. под нужды BPM Retimer)
    добавлять через `poetry add <package>`, не через `pip install` напрямую.
  - Виртуальное окружение — то, которое управляется Poetry для этого
    проекта (не создавать отдельное окружение в обход него).
  - Если модуль BPM Retimer — часть более крупного монорепозитория
    `AIMusicMasteringFactory`, уточнить: это отдельный Poetry-пакет/
    подпроект внутри репо, или он добавляется в общий `pyproject.toml`
    корня проекта?

## 11. Вопросы, которые стоит закрыть до старта разработки
1. Нужен ли рекурсивный обход подпапок в input, или только файлы в корне?
2. Нужна ли ручная корректировка автоопределённого BPM перед обработкой?
3. Обработка параллельная или последовательная — есть ли требования по
   скорости при больших объёмах файлов?
4. Платформа дашборда — веб-интерфейс (локальный сервер) или desktop-GUI?
5. Структура относительно `AIMusicMasteringFactory`: отдельный Poetry-пакет
   внутри монорепо, или зависимости добавляются в общий корневой
   `pyproject.toml`?
6. Есть ли уже установленный `rubberband-cli` в системе, или это тоже
   часть задачи по настройке окружения?

## 12. Принятые решения (08.09.2026, согласовано с заказчиком)

1. Рекурсивный обход — **да**: `retimer.scan_inputs` идёт через `rglob`,
   структура подпапок зеркалится в output.
2. Ручная корректировка BPM — **да**: колонка «Исходный BPM» редактируется
   (Enter), плюс кнопка ↻ переопределения на каждый файл.
3. Параллельность — **да**: `ThreadPoolExecutor`, число воркеров задаётся
   в дашборде (дефолт 4, лимит 1–16). Остановка — флагом между файлами.
4. Платформа дашборда — **веб**: `bmp-retimer/web/` (stdlib
   `ThreadingHTTPServer`, JSON API, ванильный JS без зависимостей),
   порт **8003** (8001 — AudioTrimmer, 8002 — LoopToToneConvertor).
5. Зависимости — **в корневой `pyproject.toml`** (`sound-mastering`):
   librosa/soundfile уже там; новых пакетов не потребовалось
   (сервер на stdlib, конвертация через системный ffmpeg).
6. `rubberband-cli` — **установлен в WSL Ubuntu** (`apt install
   rubberband-cli`, v2.0.0; в choco/winget пакета нет, официального
   Windows-инсталлера не существует). Движок `retimer` выбирает сам:
   нативный `rubberband` → `wsl rubberband` (пути транслируются
   в `/mnt/...`) → фолбэк librosa. Проверено e2e: детект клик-треков
   120→120.19 / 100→99.38, разброс 39.46/39.38 при цели 40/N=2,
   длительности сошлись до сотых.
7. Имя выходного файла: BPM округлён до целого
   (`<stem>_<bpm>bpm.<ext>`), точное значение — в таблице дашборда.
